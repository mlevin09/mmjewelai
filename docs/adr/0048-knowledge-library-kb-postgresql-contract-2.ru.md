# ADR 0048 — Контракт Knowledge Library 2.0: схема PostgreSQL `kb` как рабочий источник

Статус: утверждено Owner 21.11.2026; реализация — в Draft PR с независимой проверкой.
Не выполнение общей миграции, не релиз, не активация и не деплой. Русская копия; мастер-версия — [0048 EN](0048-knowledge-library-kb-postgresql-contract-2.md), 21.11.2026.

## Контекст и полномочия

20 ноября 2026 года Owner утвердил
[Архитектуру Knowledge Library v1.2](https://docs.google.com/document/d/17cYWdLIqPfrxWuCfvXNyMODpe-fv6_Flrk5VOJJMrWw/edit).
В ней одна схема PostgreSQL `kb` — источник истины для ревизий знаний и релизов;
опубликованные ревизии неизменяемы, состав релиза задаётся явно (`release_claims`,
`release_artifacts`); разрешения по цели использования взяты из Knowledge Library v1.6.2;
релиз закрепляется за сессией; Knowledge API — модуль существующего backend только для
чтения. Сама v1.2 не разрешает миграции, публикацию ACTIVE и деплой.

21 ноября Owner дополнительно:

- разрешил блок работ Knowledge `kb` (фазы 0, A, B1, B2, B3 из v1.2 §11) и миграции только
  в разработке и CI;
- поручил реализацию Claude в Draft PR от `jewelai-v2`, без самостоятельного слияния и
  деплоя;
- потребовал перепроверить импортируемые VERIFIED по профилям проверки до первой
  публикации (v1.2 ARCH-KB-03);
- уточнил, что возможное развёртывание в российском облаке — независимый параллельный
  проект со своим кодом и своей базой, а не реплика базы Google Cloud;
- потребовал сохранить текущую JSON-библиотеку как архив для истории, а не как рабочий
  инструмент.

v1.2 не учитывает компоненты знаний, которые уже есть в `jewelai-v2`:

- контракты Knowledge Library 1.0.0/1.1.0 (ADR 0027, 0028), с артефактами source/runtime/
  manifest/checksums в файловом хранилище (ADR 0029) и данными в `data/knowledge/`;
- неизменяемая привязка релиза к сессии `knowledge_release_binding` и выбор контракта по
  точной версии (ADR 0035, миграция 0017);
- Domain Dictionary v1.0.0 (нормализация для Parser и доменные ID для Product State);
- Rules Engine v1/v2 (единственный источник решений ask/derive/assume/block);
- параметрическая база знаний о камнях (`data/knowledge-base/v1.0.0.json`).

Кроме того, `AGENTS.md` откладывает новые профессиональные каталоги и релизы Knowledge до
решения Owner. Этот ADR фиксирует, как контракт 2.0 сосуществует с этими компонентами,
чтобы в проекте не появились две конкурирующие системы знаний.

## Решение

1. **Новый контракт, а не переписывание.** Контракт Knowledge Library 2.0.0 — это модель
   v1.2 в схеме PostgreSQL `kb`. PostgreSQL — рабочий источник содержимого 2.0, по примеру
   ADR 0044 (Roles). Ни один артефакт 1.x не конвертируется, не пересчитывает хеши и не
   переосмысляется как 2.0. Примечание к реализации: логическая схема `kb` реализована как
   таблицы `kb_*` в схеме приложения, чтобы существующая проверка Alembic и изоляция тестов
   на временной PostgreSQL по схемам работали без изменений.

2. **JSON-библиотека 1.x становится архивом.** Целевое состояние, заданное Owner
   21 ноября: сегодняшняя JSON-библиотека хранится как резервная копия для истории, а не
   как рабочий инструмент.
   - Архивный снимок сделан 21.11.2026 с коммита `jewelai-v2`
     `663070223383da27325b70be279d323fd185f831`: `data/knowledge/`, `data/knowledge-base/`,
     `specs/knowledge-library/` и `specs/knowledge-base/` (14 файлов, SHA-256 каждого — в
     `MANIFEST.json`). SHA-256 архива:
     `ee92dcbcc40f3126dc6e8ec7cbaad55f5e474b211971a460e7a832221d7e136f`. Хранится в папке
     проекта на Google Drive «Library and Matrix/Архив». Полная история изменений остаётся
     в git.
   - Пока контракт 2.0 не интегрирован (фаза C v1.2), текущий Prompt Enrichment зависит от
     runtime 1.x, поэтому в этом блоке он не удаляется.
   - После фазы C новые сессии используют только 2.0. Данные и загрузчики 1.x остаются
     только для чтения, чтобы исторические сессии можно было открыть (решение Owner,
     21 ноября).

3. **Выбор по точной версии контракта.** Потребители выбирают 2.0 только через механизм
   ADR 0035 (`PROMPT_ENRICHMENT_KNOWLEDGE_CONTRACT_VERSION=2.0.0`). Этот блок не добавляет
   и не включает это значение; интеграция потребителей (фаза C v1.2) требует отдельного
   разрешения и зависит от D5 Conversational Core.

4. **Закрепление за сессией использует существующую привязку.** Привязка 2.0 будет
   содержать ID релиза `kb`, контрольную сумму манифеста и ID ревизии политики.
   Изменение DTO привязки и миграции относится к фазе C. В этом блоке `get_release`
   отдаёт всё, что понадобится для будущей привязки, а контрольные суммы релиза
   проверяемы.

5. **Dictionary сохраняет свои полномочия.** Dictionary остаётся источником нормализации
   и доменных ID для Parser и Product State. `kb.terms`/`kb.term_relations` —
   профессиональный слой терминологии для `resolve_terms` (названия RU/EN, синонимы,
   неоднозначности, ложные эквивалентности). У `kb.entities` есть необязательное поле
   `dictionary_domain_id`. Автоматической синхронизации нет; расхождения `kb_validate`
   показывает как предупреждения.

6. **Rules Engine сохраняет свои полномочия.** `kb.rules` — квалифицированные ограничения
   из знаний, которые `evaluate_rules` возвращает как метаданные. Сами они не задают
   вопрос, не выводят, не предполагают и не блокируют. Передача их в Rules Engine
   (например как `AvailableKnowledgeFact`) — более поздняя, отдельно согласуемая работа.
   В этом блоке исполняемых правил `kb` нет, `validate_block` отключён, `evaluate_rules`
   работает только в режиме просмотра на тестовых данных.

7. **Параметрическая база знаний в этом блоке не меняется.**
   `data/knowledge-base/v1.0.0.json` не изменяется и не переносится; она входит в архивный
   снимок из решения 2. Пересечение с `kb` (например размеры камней) согласуется в более
   поздней фазе, а не молча.

8. **У каждого развёртывания своя `kb`.** Репликации между облаками нет; это заменяет
   часть v1.2 §10 о реплике. Опубликованный релиз можно выгрузить переносимым пакетом
   (ревизии, источники, термины, правила, политики, профили проверки, манифест,
   контрольная сумма) и загрузить в другое развёртывание с той же контрольной суммой.
   Пакет производный и только для чтения; его никогда не правят как второй источник.

9. **Перепроверка до публикации.** Записи v1.6.2 импортируются как черновики со своими
   K-ID. Запись публикуется как VERIFIED, только если прошла профиль проверки (точный
   источник, атомарное утверждение и scope); иначе публикуется как REFERENCE ONLY с
   записанной причиной. Единые допуски (RI ±0,01, SG ±0,03, Mohs ±0,25) и строгая
   монотонность Stuller не применяются.

10. **Проверка вызывающего.** Таблица `kb` сопоставляет ID backend-компонентов (например
    Semantic Orchestrator, консультант, тренажёр, инструменты администратора) с
    разрешёнными целями. Это backend-компоненты, а не профессиональные роли ADR 0044 и не
    права пользователей.

11. **Защита в базе данных.** Триггеры запрещают UPDATE/DELETE опубликованных ревизий и
    состава релиза. Используются две роли базы: администратор, который пишет черновики и
    вызывает функции публикации, и читатель, который видит только опубликованное. Обычные
    правки администратора идут через функции `kb_*`.

## Состав блока (фазы A–B3 v1.2)

| Фаза | Результат |
|---|---|
| A. Контракт | `specs/knowledge-library-kb/`: контракт 2.0.0, схема, словарь scope, профили проверки для атрибутов пилота, ревизия политики 1 (из v1.6.2), DTO API и типизированные ошибки |
| B1. Хранилище | Alembic-миграция `kb`, триггеры неизменяемости, роли; `kb_validate`, `kb_diff`, `kb_publish`, `kb_revert`; тесты на временной PostgreSQL |
| B2. Пилотный срез | Импорт из v1.6.2: корунд (рубин, сапфир), приблизительные размеры бриллиантов, пересчёт размеров колец, пересчёт проб, несколько ГОСТ-сплавов и обобщённые Ag 925/Pt 950 для отрицательных тестов; перепроверка; `legacy_map`; релиз `kb-2.0.0-pilot` только в разработке |
| B3. Knowledge API | Модуль только для чтения в `apps/api`; шесть операций; критерии приёмки AC-01…AC-11 по срезу и одиннадцать обязательных отрицательных тестов из v1.2 §12 |

Не входит: интеграция с SO и IFP (AC-12), включение контракта 2.0 в конфигурации runtime,
выполнение миграций на общей базе или preprod, активация ACTIVE, деплой, перенос всего
корпуса (фаза D) и любые изменения Dictionary, Rules, параметрической базы знаний или
артефактов Knowledge 1.x.

## Решения Owner по открытым вопросам

1. Исторические сессии 1.x должны оставаться доступными для просмотра после фазы C
   (Owner, 21 ноября). Данные и загрузчики 1.x сохраняются только для чтения исторических
   сессий; новые сессии их никогда не используют.

## Альтернативы

- **Заменить runtime 1.x на `kb` и перенести старые сессии.** Отклонено: переписывает
  исторические идентичности, которые ADR 0035 запрещает переосмыслять.
- **Компилировать `kb` в файловые артефакты 1.1.** Отклонено: модель 1.1 нацелена на
  политики Product State, в ней нет разрешений по цели и состава релиза; кроме того,
  файлы стали бы вторым авторитетным путём вопреки принципу 1 v1.2.
- **Хранить терминологию `kb` в Dictionary.** Отклонено: Dictionary — ограниченный
  проверенный набор нормализации для Parser со своим жизненным циклом.
- **Отдельный микросервис.** Отклонено в v1.2: API — модуль существующего backend.
- **Репликация базы между облаками.** Отклонено Owner 21 ноября: развёртывания —
  независимые проекты.

## Последствия

- Две линии контрактов знаний сосуществуют до фазы C; после неё 1.x — только архив.
- Терминология может быть определена и в Dictionary, и в `kb`; расхождения видны через
  предупреждения проверки, пока не принято решение о согласовании.
- Создание ролей и триггеров в Cloud SQL требует достаточных прав у миграции; это
  проверяется до любого запроса на общую миграцию.
- Публикация пилота доказывает контракты хранения и API, а не профессиональную полноту
  библиотеки.

## Проверка

Тесты фазы B выполняются на временной PostgreSQL, прошедшей существующую проверку
безопасности. Они должны покрыть как минимум: идемпотентную публикацию и типизированный
конфликт при другом содержимом; отказ UPDATE/DELETE опубликованных строк и состава;
неизменность данных релиза N после публикации N+1; фильтрацию по цели согласно ревизии
политики релиза; типизированные ошибки для неизвестного или недоступного релиза;
перепроверку по профилям (Mohs как порядковое или интервальное значение, одинаковые
диаметры Stuller для разных масс допустимы); обобщённые Ag 925/Pt 950 никогда не
VERIFIED; плотности ГОСТ-сплавов и рекомендации ухода никогда не возвращаются для
`purpose=prompt`; неоднозначности и ложные эквивалентности в `resolve_terms`;
`review_required` при конфликте источников; правила только в режиме просмотра; отсутствие
записей в Product State; полную запись `legacy_map` для каждого импортированного K-ID.
